# Ручное (Manual) тестирование для .NET и Unity разработчика

## Введение

Многие разработчики считают тестирование задачей QA-инженера. На практике сильный разработчик умеет самостоятельно проводить качественное ручное тестирование своих функций до передачи их на ревью, QA или заказчику.

Для Unity и .NET проектов стоимость пропущенного дефекта особенно высока:

* В бизнес-приложении ошибка может привести к потере данных.
* В игре ошибка может ломать прогрессию, монетизацию или игровой опыт.
* Исправление бага после релиза может стоить в десятки раз дороже, чем на этапе разработки.

Цель данного материала — сформировать у разработчика системный подход к ручному тестированию.

# Глоссарий по тестированию ПО

Ниже — базовый глоссарий, который удобно использовать как справочник для .NET и Unity-разработчика. Термины расположены от общих понятий к более специализированным.

## 1. Основные понятия

| Термин                     | Определение                                                                                             | Пример                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **Software Testing**       | Процесс проверки программного обеспечения с целью выявления дефектов и оценки соответствия требованиям. | Проверка работы покупки машины в игре.                             |
| **Manual Testing**         | Тестирование, выполняемое человеком без автоматизированных тестов.                                      | QA вручную проходит регистрацию пользователя.                      |
| **Automated Testing**      | Тестирование, выполняемое программами и тестовыми скриптами.                                            | Unit Test проверяет метод расчёта цены.                            |
| **QA (Quality Assurance)** | Совокупность процессов, направленных на обеспечение качества продукта.                                  | Code Review, тестирование, анализ требований.                      |
| **QC (Quality Control)**   | Контроль качества готового или создаваемого продукта посредством выявления дефектов.                    | Проверка сборки перед релизом.                                     |
| **Tester / QA Engineer**   | Специалист, занимающийся проверкой качества программного продукта.                                      | Тестировщик проверяет новую игровую механику.                      |
| **Developer Testing**      | Тестирование, выполняемое самим разработчиком.                                                          | Перед передачей задачи QA разработчик проверяет основные сценарии. |

# 2. Требования и ожидаемое поведение

| Термин                         | Определение                                                                  | Пример                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Requirement**                | Требование к системе или функциональности.                                   | «Пользователь может купить машину за 1000 монет».                      |
| **Functional Requirement**     | Требование, описывающее конкретное поведение системы.                        | Кнопка «Купить» должна приобрести машину.                              |
| **Non-functional Requirement** | Требование к характеристикам системы, а не к конкретной функции.             | Игра должна работать минимум при 30 FPS.                               |
| **Acceptance Criteria**        | Условия, которым должна соответствовать задача, чтобы считаться выполненной. | После покупки машина появляется в гараже и деньги списываются.         |
| **Expected Result**            | Ожидаемый результат выполнения теста.                                        | После покупки баланс уменьшается на 1000.                              |
| **Actual Result**              | Фактический результат, полученный при тестировании.                          | Баланс уменьшился на 2000.                                             |
| **Test Scenario**              | Высокоуровневое описание того, что необходимо проверить.                     | Проверить покупку автомобиля.                                          |
| **Test Case**                  | Конкретный набор шагов, входных данных и ожидаемого результата.              | Открыть магазин → выбрать машину → нажать «Купить» → проверить баланс. |

# 3. Дефекты

| Термин         | Определение                                                                                        | Пример                                                             |
| -------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **Bug**        | Ошибка или дефект в программном обеспечении, приводящий к неправильному поведению.                 | После покупки машина не появляется в гараже.                       |
| **Defect**     | Несоответствие фактического поведения программного продукта требованиям или ожидаемому результату. | Система принимает отрицательное количество товара.                 |
| **Error**      | Ошибочное действие или решение человека, которое может привести к дефекту.                         | Разработчик использовал `>` вместо `>=`.                           |
| **Failure**    | Проявление дефекта во время выполнения программы.                                                  | Игра падает при открытии магазина.                                 |
| **Crash**      | Аварийное завершение приложения.                                                                   | Unity-приложение закрывается при загрузке сцены.                   |
| **Regression** | Ситуация, когда ранее работавшая функциональность перестала работать после изменений.              | После изменения сохранений перестала загружаться купленная машина. |

### Важное различие

Полезно запомнить цепочку:

**Error → Defect → Failure**

Например:

> Разработчик допустил ошибку → в коде появился дефект → пользователь столкнулся с неправильным поведением.

# 4. Приоритет и серьезность бага

Это особенно важно при работе QA.

| Термин       | Определение                                         |
| ------------ | --------------------------------------------------- |
| **Severity** | Насколько серьезно дефект влияет на работу системы. |
| **Priority** | Насколько срочно необходимо исправить дефект.       |

Например:

### Critical Severity + High Priority

Игра падает при запуске.

### Low Severity + High Priority

В главном меню написано название компании с ошибкой.

Функциональность работает, но ошибка может быть критична для релиза.

### High Severity + Low Priority

Редкая функция администратора ломается, но обычные пользователи ей не пользуются.

# 5. Основные виды тестирования

| Термин                     | Определение                                                                                               |
| -------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Smoke Testing**          | Быстрая проверка основных функций системы после получения новой сборки.                                   |
| **Sanity Testing**         | Проверка конкретной измененной области после небольших изменений.                                         |
| **Regression Testing**     | Проверка существующей функциональности после изменений.                                                   |
| **Functional Testing**     | Проверка соответствия функциональности требованиям.                                                       |
| **Non-functional Testing** | Проверка характеристик системы: производительности, безопасности, удобства и т. д.                        |
| **Exploratory Testing**    | Исследовательское тестирование без жесткого сценария, когда тестировщик самостоятельно исследует систему. |
| **Ad-hoc Testing**         | Неформальная проверка без заранее подготовленного тестового сценария.                                     |
| **Acceptance Testing**     | Проверка того, удовлетворяет ли продукт требованиям заказчика или пользователя.                           |
| **Usability Testing**      | Проверка удобства использования приложения.                                                               |
| **Compatibility Testing**  | Проверка работы приложения в различных окружениях.                                                        |

# 6. Уровни тестирования

Очень важная классификация для разработчика.

### Unit Testing

Проверка отдельного небольшого компонента.

Например:

```csharp
CalculatePrice()
```

проверяется отдельно от остальной системы.

---

### Integration Testing

Проверка взаимодействия нескольких компонентов.

Например:

```text
Game → SaveSystem → File
```

Проверяется не только `SaveSystem`, но и его взаимодействие с файловой системой.

---

### System Testing

Проверка всей системы как единого продукта.

Например:

```text
Запуск игры
↓
Гараж
↓
Выбор машины
↓
Гонка
↓
Награда
↓
Сохранение
```

---

### Acceptance Testing

Проверка продукта с точки зрения требований пользователя или заказчика.

Например:

> Пользователь может пройти гонку, получить награду и увидеть её после перезапуска игры.

| **Negative Testing**         | Проверка некорректных данных и нештатных сценариев.                                      |

# 8. Граничные значения

**Boundary Value** — значение, находящееся на границе допустимого диапазона.

Например:

```text
Допустимый диапазон: 1–100
```

Хороший набор тестов:

```text
0
1
2
99
100
101
```

Почему это важно?

Именно на границах часто возникают ошибки:

```csharp
if (value > 100)
```

вместо:

```csharp
if (value >= 100)
```

---

# 9. Эквивалентные классы

**Equivalence Partitioning** — разделение входных данных на группы, внутри которых система должна вести себя одинаково.

Например:

```text
Возраст: 18–60
```

Получаем:

```text
< 18       → недопустимые
18–60      → допустимые
> 60       → недопустимые
```

Можно проверить всего три значения:

```text
15
30
70
```

вместо проверки всех возможных возрастов.

# 11. Жизненный цикл бага

Типичный жизненный цикл:

```text
New
 ↓
Assigned
 ↓
In Progress
 ↓
Fixed
 ↓
Ready for Testing
 ↓
Retest
 ↓
Verified
 ↓
Closed
```

Если ошибка осталась:

```text
Retest
   ↓
Failed
   ↓
Reopened
   ↓
Developer
```

### Основные состояния

**New** — баг обнаружен.

**Assigned** — назначен разработчику.

**In Progress** — разработчик работает над исправлением.

**Fixed** — разработчик считает баг исправленным.

**Ready for Testing** — новая версия доступна для проверки.

**Reopened** — ошибка все еще существует.

**Verified** — QA подтвердил исправление.

**Closed** — задача полностью закрыта.

# 12. Retest и Regression

Эти термины часто путают.

### Retest

Проверяем:

> Исправили ли конкретный баг?

Например:

> В версии 1.2 исправили падение при покупке машины.

QA повторяет именно этот сценарий.

---

### Regression Testing

Проверяем:

> Не сломалось ли что-нибудь еще после исправления?

После исправления покупки машины дополнительно проверяем:

* магазин;
* валюту;
* гараж;
* сохранение;
* выбор машины.

**Коротко:**

> Retest — проверяем исправление конкретного бага.
> Regression — проверяем, что изменения ничего не сломали.

# 15. Аутентификация и авторизация

Эти термины тоже важно не путать.

### Authentication

> Кто ты?

Например:

```text
Login + Password
```

---

### Authorization

> Что тебе разрешено?

Например:

```text
User → может просматривать профиль

Admin → может удалять пользователей
```

Запомнить можно так:

**Authentication = Кто?**

**Authorization = Что разрешено?**

---

# 16. Black Box / White Box / Gray Box

### Black Box Testing

Тестировщик не знает внутреннего устройства программы.

Проверяется:

```text
Input → System → Output
```

Например:

Пользователь нажимает кнопку и смотрит результат.

---

### White Box Testing

Тестировщик знает внутреннюю структуру программы.

Например, разработчик проверяет:

```csharp
if
else
switch
```

и разные ветки выполнения.

---

### Gray Box Testing

Комбинация двух подходов.

Тестировщик знает часть внутреннего устройства системы.

### Главное правило

При ручном тестировании разработчик должен постоянно задавать себе четыре вопроса:

> **Что должно произойти?**
> **Что произойдет при неправильных данных?**
> **Что произойдет на границе допустимого?**
> **Что я могу сделать как пользователь, чего разработчик не предусмотрел?**

Именно эти четыре вопроса дают очень хорошую основу для самостоятельного QA-подхода в .NET и Unity-разработке.
